# Systra Design DNA 2.0: reference-first design

This is a visual vocabulary derived from inspecting 40 existing Systra library preview images, with 34 selected examples. Observations describe visible static composition, not verified animation, source code, license, current availability or accessibility. See the [reference index](reference-index.md). Do not infer a working interaction from its component name or still image.

## Expanded design workflow (optional lookup)

1. Identify the section's job and the visual subject that can communicate it. Choose a direction below based on content, not a palette.
2. Inspect **one or two relevant actual visual references** of different compositions before writing JSX. When the authorized Systra Tools MCP is connected, search for suitable sections, inspect their available previews and source as permitted by access. Otherwise use authorized project images or the user's own screenshots. An offline text index is a fallback, not visual evidence. Do not claim images were seen if only names or descriptions were read.
3. Record the one or two most relevant observations: focal subject, hierarchy, material or interaction. Never copy a distinctive layout, image or text verbatim from a third-party site.
4. Build a short direction sheet: focal subject, dominant visual area, reading order, palette roles, display/body fonts, one interaction, and asset requirements. Reject generic dashboard/cards unless they are specifically needed.
5. Compare two truly different composition ideas briefly before choosing. At least one should not be a conventional split or equal-card grid. The reference establishes a quality bar, not a reusable theme.
6. Use genuine Hugeicons for needed functional icons and actual project assets for imagery. Without required assets, ask or state the limitation; do not fake a premium scene with gradients and random geometry.
7. Render and inspect the result against actual reference observations. If the draft looks like a stock template, revise architecture and focal subject before changing colors. When tools exist, make one focused screenshot-led revision for material defects and verify it. Record visual and functional gates separately.
8. If actual visual references or browser rendering are unavailable, mark the reference or render gate NOT TESTED; do not certify visual quality. A working build is not proof of strong art direction.

## Six directions

| Direction | Visual grammar | Avoid |
| --- | --- | --- |
| Editorial | Strong headline and controlled wraps, asymmetric image/text rhythm, confident typography, one editorial crop | Decorative badges and empty giant whitespace |
| Minimal | One clear subject, text-led hierarchy, neutral surface, precise optical spacing, a few semantic Hugeicons | Sterile default SaaS cards, tiny type, uniform grid |
| Experimental | A spatial metaphor, transformation, inline media or movable specimen; one rule ties elements together | Random blobs, confetti, animation without meaning |
| Luxury | Tactile photography, editorial serif contrast, carefully composed crop, quiet controls | Gold gradients, excessive serif italics, illegible glass |
| Technical | Readable interactive specimen, precise diagrams, restrained mono labels, visible state | Fake analytics, unreadable terminal, unrelated metrics |
| Immersive | One compelling scene, text-safe region, a coherent image-derived palette, layered content | Busy background under text, disconnected thumbnails, theatrical loading |

## Reference access and distribution

The public skill ships a text-only index and original implementation primitives. Visual preview files and premium source stay in their authorized environment. Use the optional MCP only under its access rules; do not bundle screenshots or component code from premium entries. An owner may keep a separate private visual atlas. This preserves offline use without pretending the offline index is a substitute for seeing references.

Reference IDs are library preview filenames observed during review, not guarantees of MCP identifiers. Search by name and category, verify the returned result, respect authorization and never fabricate a match.

## Design comparisons

- Weak hero: small generic heading + gradient dashboard. Better: a singular readable product moment or a meaningful cinematic crop that belongs to the product.
- Weak process: three equal cards + arrows. Better: one transformable object, a trace line, a scrubber or a connected sequence.
- Weak pricing: identical panels with a highlighted middle. Better: a selection architecture or an intentional material world, with accessible comparison.
- Weak proof: generic stars and fake avatars. Better: actual quote hierarchy, real attribution, verified results or an explicitly illustrative example.
- Weak features: cards repeating their icons. Better: a demonstrated task, typographic cloud, spatial diagram or an editorial specimen.
- Weak motion: fade every element. Better: one readable state handoff, with a static reduced-motion version.

Use the [motion and controls](interaction-atlas.md) after the composition is decided. No effect is compulsory if the content is better without it.
